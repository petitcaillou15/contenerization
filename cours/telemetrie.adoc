== Observabilité et télémétrie

=== Pourquoi observer ?

* Une application cloud-native est faite de *nombreux services*, éphémères
* Quand quelque chose ne va pas : *où ?* *depuis quand ?* *pourquoi ?*
* L'observabilité = pouvoir *comprendre l'état interne* d'un système à partir de ce qu'il produit

=== Les trois piliers

[cols="1,3"]
|===
| *Logs* | Des événements horodatés : « que s'est-il passé ? »
| *Métriques* | Des valeurs numériques dans le temps : « combien ? à quelle vitesse ? »
| *Traces* | Le parcours d'une requête à travers plusieurs services : « où est-ce lent ? »
|===

Dans ce projet : *logs* et *métriques*. Les traces sont hors programme.

=== Les logs dans Kubernetes

* Une application cloud-native écrit ses logs sur la *sortie standard* (stdout / stderr)
* Kubernetes les récupère :

[source,bash]
----
kubectl logs <pod>
kubectl logs <pod> -f                 # suivre en direct
kubectl logs <pod> --previous         # conteneur précédent (après un crash)
kubectl logs -l app=web               # tous les Pods d'un label
----

* Un Pod supprimé *emporte ses logs* : d'où l'intérêt de les *centraliser* (ELK, Loki...)

=== Les métriques

* Les services exposent des métriques à un format standard (*Prometheus*), souvent sur `/metrics`
* *Prometheus* vient les *collecter* régulièrement (modèle _pull_)
* *Grafana* les affiche dans des tableaux de bord

[source,bash]
----
curl http://<service>/metrics
----

Compteurs, jauges, durées des requêtes... et des *métriques métier*.

=== Les ressources du cluster : metrics-server

[source,bash]
----
minikube addons enable metrics-server
kubectl top pods -n <namespace>
kubectl top nodes
----

CPU et mémoire consommés par les Pods et les nœuds.

=== Ce qu'on vous demandera

À la séance de soutenance, il faudra *montrer* :

* les *logs* d'un composant
* *au moins une métrique* (l'endpoint `/metrics` d'un service, ou `kubectl top`)

*Facultatif* (valorisé en bonus) : ELK, Prometheus + Grafana, tableaux de bord.
